## Matching, transaction and idempotency

The trusted PostgreSQL implementation loads the eligible session roster under the same session row lock used by joins/removals/closure. It accepts 3–100 members within configured capacity, performs Fisher–Yates with cryptographic random values, then gives each shuffled participant the next ID, wrapping the final ID to the first. This always produces one complete cycle and handles odd/even counts. A recursive validation verifies full-cycle coverage; constraints verify one recipient/giver, distinct IDs and valid same-session membership.

Randomness comes from PostgreSQL `gen_random_uuid()` (UUIDv4, generated by the server cryptographic RNG), using its first 32 entirely random bits. Rejection sampling removes modulo bias before selecting a Fisher–Yates index. Version/variant bits are not sampled. No `Math.random()`, client-generated permutation or caller-supplied assignment map is used.

The public RPC runs one database transaction. Closure and the membership lock are retained outside a nested matching subtransaction. Assignment insertion, matched timestamp, generic activation and success notifications all succeed together or all roll back. On failure, only `draw_failed`, a generic deduplicated host notice and a durable retry activity remain; no SQL error detail or private IDs are logged/stored in failure messages. The original API still returns a lobby document showing the failure state, so the transaction is not undone by an exception escaping the RPC. A retried successful draw returns the same existing result and timestamp without generating a new permutation.

Concurrent requests serialize on the session row. Both unique assignment keys are enforced in the database. Composite membership FKs are deferrable to commit, allowing whole-session cascade cleanup without weakening final referential integrity. Once drawing begins, the DB roster trigger blocks membership mutation; the module's existing closed/deadline checks also reject joining and host management. Generic start/leave/cancel APIs continue through the dedicated module boundary. There is no redraw or reroll UI.

## Automatic scheduling and season start

Existing joining-close events call the extended closure helper, which inserts exactly one `secret_santa_draw` lifecycle activity per session. The normal bounded scheduler picks it up, verifies closure/eligibility, invokes the same draw, and completes the activity only on success. Failure keeps a scheduled event with exponential retry backoff. An insufficient lobby is not drawn. Already-ready existing lobbies receive a draw event during migration.

Deadline closure and matching can span two existing scheduler ticks; they do not depend on the app being open. `drawing` is an internal transaction state and need not be externally visible for a short successful draw. `matched_at` is the canonical season start. Exchange DATE and validated IANA timezone remain recorded in settings. Generic `started_at` is set by the existing activation trigger. Enabled future activities are configuration only: no fake gameplay, unlocks, completion/XP events or questions are created.

## Privacy, notifications and deleted accounts

`private.secret_santa_assignments` has RLS and no PUBLIC/anon/authenticated table grants or policies; it is absent from the exposed client schema. Its private helpers are denied ordinary execution. The public SECURITY INVOKER lobby RPC reaches one private authorized dispatcher with an empty fixed search path. It derives the user from the live authenticated session, checks membership and matching, and looks up only that user's giver row. Unknown payload fields, including any giver ID, are rejected. Hosts receive no broader access.

Before explicit reveal, the response contains no recipient name. Reveal persists `revealed_at` idempotently; subsequent retrieval returns only the recipient's current permitted display name and availability, alongside nonsecret game settings. No other relationship, recipient UUID or identity of the user's giver is returned. Sensitive response data is held in account-scoped component memory and never persisted in AsyncStorage, localStorage or another client disk cache. The UI conceals recipient content on app background events; OS snapshot timing remains a physical-device check.

Four new templates are registered: `secret_santa_draw_started`, `secret_santa_assignment_ready`, `secret_santa_draw_failed`, `secret_santa_game_started`. Started and game-start events are in-app with push suppressed for the instantaneous draw; assignment-ready pushes are queued normally, failure notices target the host. All content is static and generic: no recipient names or relationship data enter notification bodies or provider payloads. Existing notification preferences, quiet hours, delivery guards and retries remain authoritative. Unique per-session/per-user event keys prevent duplicates.

Matched host/participant account deletion preserves assignment integrity through a private UUID-only account reference table and replacement session/member FKs. Insert guards still require live accounts. Deleted profiles/auth sessions disappear, surviving membership rows display `Participant unavailable`, and `recovery_required` is set. No old display names, email or credentials are retained in the reference table. Unmatched hosted sessions/membership retain prior deletion behavior through the deletion trigger. There is no automatic host succession or recovery policy for a matched exchange; the UI surfaces the issue instead of redrawing.
